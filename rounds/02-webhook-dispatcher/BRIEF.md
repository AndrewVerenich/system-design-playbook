## Задача

Спроектировать сервис **доставки webhooks**: другие сервисы (или твой API) регистрируют HTTP-endpoint и получают POST с событием, когда что-то произошло в системе.

Пример: `order.paid` → `POST https://customer.example/hooks/orders` с JSON-телом.

---

## Функциональные требования (стартовый скоуп — уточним вместе)

**Must have (ориентир)**

- Зарегистрировать webhook: URL + список event types (или `*`)
- Принять событие на вход (внутренний API / очередь) и **доставить** подписчикам
- Повторные попытки при неуспехе (5xx, timeout, сеть)
- Идемпотентность / защита от бесконечных дублей на стороне доставки (обсудим)
- Просмотр статуса доставки (хотя бы: pending / success / failed)

**Nice to have**

- Подпись запроса (HMAC secret)
- Disable endpoint после N фейлов (circuit / auto-disable)
- DLQ / dead letter для ручного разбора

**Вне скоупа v1 (пока)**

- Полноценный UI портал для клиентов
- Fan-out в Kafka для аналитики
- Гарантия exactly-once у consumer’а заказчика (мы даём at-least-once)
- Rate limiter как отдельный продукт (можно простой лимит later)

---

## Нефункциональные цели (ориентир — зафиксируем на старте обсуждения)

| NFR | Ориентир |
|-----|----------|
| Входящие события | peak ~200/s |
| Среднее число подписчиков на event | ~5 (пик на популярный тип выше) |
| Latency «принять событие» | p99 &lt; 100 ms (не ждать чужой HTTP) |
| Доставка | async; первая попытка ASAP |
| Availability приёма событий | 99.9% |
| Чужой endpoint медленный/лежит | не должен ронять dispatcher |

Ключевая идея раунда: **нельзя** синхронно ходить на customer URL в том же запросе, что принял событие.

---

## На что обратить внимание (без готового решения)

1. Синхронный accept vs async delivery  
2. Retry / backoff / max attempts  
3. Timeout на outbound HTTP  
4. Что считать успехом (2xx? только 200?)  
5. Ordering: нужен ли порядок событий на один endpoint  
6. Секреты и HMAC  
7. Storm: один упавший endpoint + тысячи ретраев  

Не тащи весь saga-orchestrator — система должна остаться простой.

## Зачем эта задача после Pastebin

Pastebin = read/write KV + TTL.  
Webhook dispatcher = **async fan-out + retries + failure isolation** — следующий слой сложности без rate-limiter и без «большой» messaging-платформы с нуля (Kafka можно предложить сам, если обоснуешь).
